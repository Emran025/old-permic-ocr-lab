# دليل تدريب Colab والاستئناف من GitHub لمختبر OCR البرمية القديمة

## الغرض والحدود العلمية

الدفتر `training/notebooks/old_permic_synthetic_generation.ipynb` هو مصدر التنفيذ الوحيد للتوليد والتدريب. يولّد محارف **Old Permic** منفصلة من الخط، ويتحقق من وسوم YOLO، ويدرّب baseline صناعيًا، ويحفظ أحدث نقطة استئناف قابلة للتحقق، ثم يبني إصدار نتائج مستقلًا. نجاح baseline الصناعي لا يثبت أداء OCR على المخطوطات التاريخية.

> يدفع الدفتر في المرة الأولى **snapshot كاملًا للمرحلة الصناعية**: `images/` و`labels/` و`class_map.json` و`manifest.json` و`assets.jsonl`، ثم يدفع بعد كل epoch أحدث `last.pt` و`results.csv` و`data_contract.json` و`resume_state.json`. لا يرفع صورًا حقيقية أو أسرارًا أو بيانات خاصة.

## ما الذي يُحفَظ بعد كل epoch؟

| المسار | المحتوى | السياسة |
|---|---|---|
| `main` | كود المشروع والدفتر والخط والمولد | لا يضم بيانات التدريب أو checkpoints. |
| `colab-checkpoints` | بيانات المرحلة الصناعية المتحققة، وأحدث `last.pt` وmetadata للتجربة | تُدفع البيانات قبل التدريب مرة واحدة ثم يُستبدل آخر checkpoint بعد كل epoch؛ لا يحتفظ بتاريخ وزن لكل epoch. |
| `colab-results` | إصدار مقبول بعد `test` ومراجعة بشرية | لا يُنشر تلقائيًا؛ يتطلب `PUBLISH_RELEASE = True`. |

يستخدم فرع `colab-checkpoints` commit واحدًا يُعدَّل ثم يُدفع بـ`--force-with-lease` في كل epoch. هذا يحقق الاستئناف من GitHub من دون تضخيم المستودع بسلسلة طويلة من نسخ الوزن. لا تشغّل جلستين تدفعان إلى **التجربة نفسها** في وقت واحد.

> المستودع عام؛ لذلك تكون الملفات في فرع `colab-checkpoints` عامة أيضًا. لا تضع صورًا خاصة أو بيانات حقيقية محمية أو أسرارًا داخل هذا المسار.

## تشغيل التدريب أو الاستئناف

| الخطوة | الإجراء | ناتج التحقق |
|---|---|---|
| 1 | افتح الدفتر من الرابط العام للمستودع في Colab، واختر Runtime مزودًا بـGPU. | خلية البيئة تطبع GPU وتفشل صراحةً إن لم يتوفر CUDA. |
| 2 | شغّل البيئة والاستنساخ وإعداد GitHub وبصمة الخط. | يستنسخ المشروع بلا token قراءة، وتطابق بصمة الخط `f2eb…73006`. |
| 3 | ابدأ بـ`STAGE = "S0"` فقط، وشغّل خلية استعادة snapshot. | تستعيد البيانات إن وُجدت، أو يولدها الدفتر حتميًا ثم يدفعها قبل التدريب. |
| 4 | راجع معاينة الصناديق. | لا تبدأ التدريب إن كانت المحارف أو المربعات غير سليمة. |
| 5 | شغّل إعداد التدريب وأدوات checkpoint ثم خلية التدريب. | يتحقق من Secret الكتابي، ويستعيد `last.pt` أو يبدأ تجربة جديدة؛ لا يخفي فشل الدفع أو يبدأ من الصفر عند تعارض snapshot. إذا كان `saved_after_epoch >= EPOCHS` فلا يستدعي `resume=True`؛ يجهز الوزن النهائي وينقلك إلى test. |
| 6 | اترك التدريب مستمرًا. | بعد كل epoch تُدفع آخر نقطة إلى `colab-checkpoints`. |
| 7 | بعد انتهاء التدريب، شغّل `test` وبناء `release.json` ثم راجع النتائج. | يظل الإصدار `evaluated-not-published` حتى قرار نشر صريح. |

عند فتح جلسة أو حساب جديد، شغّل التسلسل ذاته واضبط `STAGE` و`EXPERIMENT_NAME` على التجربة نفسها. تستعيد خلية الاستعادة المبكرة بيانات المرحلة من `colab-checkpoints` قبل التوليد؛ ثم يتحقق الدفتر من الصور والوسوم والعقد، ويستعيد خلية التدريب `last.pt` تلقائيًا. إذا بلغ checkpoint عدد epochs المستهدف، تتوقف خلية التدريب بنجاح من دون استئناف وتضع `last.pt` النهائي في `BEST_PT` لخلية test التالية. إذا اختلفت **هوية المولد فقط** بينما تطابقت بصمات `manifest.json` و`class_map.json` و`assets.jsonl`، يعيد الدفتر بناء metadata وsnapshot البيانات لكنه يحتفظ بـ`last.pt` و`resume_state.json` ويستأنف التدريب. أما إذا اختلفت بيانات المرحلة فعلًا، فيسجل عدم المطابقة، ويعزل artifacts الخاصة بالتجربة غير المتوافقة، ثم ينشئ بيانات المرحلة الحالية حتميًا ويدفع snapshot مستقلًا قبل epoch الأول.

### استغلال ذاكرة T4 في baseline S0

يبدأ الإصدار `baseline_v2_batch8` بـ`batch=8`، وهو ضعف baseline السابق، مع `AMP` و4 عمال تحميل كحد أعلى. لا يرفع هذا `IMAGE_SIZE` أو عدد epochs أو بيانات S0. إذا ظهر خطأ CUDA OOM، تعيد الخلية التجربة تلقائيًا بحجم `6` ثم `4` فقط؛ ولا تستمر على CPU. وتطبع الخلية في نهاية كل epoch الذاكرة المحجوزة والحد الأقصى المستخدم من GPU، لذلك يجب الحكم على الاستهلاك من خرجها الفعلي لا من تقدير ثابت.

لا تدمج بيانات S0 وS0-d1 ولا تستأنف optimizer الخاص بـS0. بعد قبول S0، تبدأ S0-d1 **بتكييف وزن S0 المؤرشف فقط** ثم تنشئ optimizer وبيانات وcheckpoint خاصة بها. يطبّق الدفتر العقد نفسه على S1 وS2: وزن المرحلة السابقة المقبولة هو تهيئة فقط، بينما يبقى الاستئناف محصورًا في المرحلة الحالية. التدرج تنظيم بصري وتعليمي؛ تبقى وحدة التدريب والتوسيم **حرفًا** لا كلمة ولا معجمًا.

## مسار البيانات الحقيقية المراجعة من الموقع

يحتوي تبويب **الوسم** في الموقع على مشروع دائم لكل باحث. يمكن إضافة صورة من مدونة المصادر أو رفع صورة جديدة؛ تحفظ الصورة الجديدة في تخزين المشروع، بينما تحفظ لكل صورة بيانات المصدر والحقوق والصفحة وحالة المراجعة والتقسيم وصناديق YOLO. لا تتحول الصورة إلى مثال تدريب لمجرد رفعها أو رسم صندوق واحد.

تُسمح حزمة `old_permic_real_labeled_v1.zip` فقط عندما تكون كل الصور المرشحة بحالة `reviewed` أو `approved`، وفيها صناديق محارف مرئية، وقيم `train` و`val` و`test`، ولا تظهر الصفحة الأصلية نفسها في أكثر من تقسيم. يصدر الموقع داخل ZIP البنية المطابقة للمدقق: `images/` و`labels/` و`class_map.json` و`manifest_real.json` و`sources.csv`.

| الخطوة | الإجراء في الموقع أو Colab | بوابة الأمان |
|---|---|---|
| 1 | أضف صورة مصدر أو صورة جديدة إلى مشروع الوسم، ثم وثّق المصدر والحقوق والصفحة. | تبقى `in_progress` ولا تدخل التصدير. |
| 2 | ارسم مربعات للمحارف المقروءة فقط، وعيّن التقسيم وحالة `reviewed` أو `approved`. | يرفض الموقع اعتماد صورة بلا صناديق أو تقسيم. |
| 3 | اختر **تصدير المراجَع**. | يرفض التصدير عند غياب train أو val أو test أو عند تسرّب صفحة بين تقسيمين. |
| 4 | ارفع ZIP الناتج إلى `/content` في Colab واضبط `REAL_DATA_ARCHIVE`. | خلية `PREPARE_REAL_MANUSCRIPT_DATA` تشغّل المدقق المستقل وتطابق `class_map.json`. |
| 5 | بعد مراجعة خرج المدقق، فعّل `RUN_REAL_MANUSCRIPT_FINETUNE`. | يستعمل وزنًا صناعيًا محددًا من `colab-checkpoints` ولا يبدأ من وزن غير موثق. |
| 6 | شغّل تقييم test المنفصل فقط بعد التكييف. | لا ينشر الخرج ولا يربط الاستدلال بالموقع تلقائيًا. |

يحفظ مسار التكييف الحقيقي إلى GitHub **الأوزان والعقود وحالة الاستئناف فقط**؛ لا يدفع ZIP أو صور المخطوطات الحقيقية. يرفض الدفتر التدريب إذا اختلف ترتيب الفئات عن baseline الصناعي، أو كانت الحزمة أقل من ثلاث صفحات/مصادر مستقلة، أو قلّت عن عشرة صناديق محارف. هذه حدود تنفيذية دنيا وليست ادعاءً بأن حجم البيانات كافٍ علميًا لإثبات OCR تاريخي.

### تجربة S0-d1: محرف أصغر في مواضع متعددة

بعد قبول S0 فقط، اضبط `STAGE = "S0-d1"`. لا يغيّر ذلك S0 المؤرشفة أو يعيد كتابة checkpoint الخاص بها. يستنسخ الدفتر وزن S0 المثبت عند epoch 100 من فرع `s0-epoch100-checkpoint` بعد التحقق من بصمته، ثم يبدأ تدريب S0-d1 جديدًا؛ لا يستدعي `resume=True` لـS0 ولا يعيد optimizerها. تولد S0-d1 محرفًا واحدًا في كل صورة، لكن بحجم نسبي أصغر وفي واحدة من ثماني مناطق صفحة آمنة خارج المركز، مع التدوير والضجيج المحدودين في profile `controlled-deformation`. يبقى لكل صورة مربع YOLO واحد، ولا تُولد كلمات أو أسطر في هذه المرحلة.

تستخدم S0-d1 تجربة مستقلة باسم `old_permic_s0_d1_scattered_v1_batch32_e60`، و60 epoch بدل 100. يبدأ وزن النموذج من S0، لكن التقدم داخل S0-d1 وحده هو ما يُحفظ ويُستأنف بعد ذلك. تبدأ الخلية بـ`batch=32` لاستعمال T4 بصورة أعلى، ثم تتراجع تلقائيًا إلى `24` و`16` و`12` ثم `8` إذا ظهر CUDA OOM. لا تغير `IMAGE_SIZE` أو batch يدويًا قبل تسجيل نتيجة المحاولة؛ حفظت هذه الخطة لتبقى مقارنة S0-d1 قابلة للإعادة مع S0.

## صلاحية الكتابة إلى GitHub

القراءة العامة لا تحتاج إلى secret. لكن الدفع التأسيسي للبيانات والدفع اللاحق لكل epoch يستخدمان **Colab Secret** باسم `GITHUB_WRITE_TOKEN`؛ لا تعتمد الخلية على حالة تسجيل الدخول في واجهة Colab ولا تكتب السر في الملف أو commit أو `git remote`.

1. أنشئ في GitHub fine-grained token للمالك `Emran025` والمستودع `old-permic-ocr-lab` فقط.
2. امنح **Repository permissions → Contents: Write** فقط، مع انتهاء قصير.
3. أضف القيمة في Colab ضمن **Secrets** باسم `GITHUB_WRITE_TOKEN`؛ لا تضعها داخل خلية أو ملف أو commit.
4. ابدأ التدريب. إذا تعذر دفع epoch، تتوقف callback بخطأ واضح بدل أن تدّعي أن checkpoint حُفظ.
5. ألغ token أو احذفه عندما لا يعود مطلوبًا.

عند تشغيل خلية **النشر النهائي** بعد تفعيل `PUBLISH_RELEASE = True`، تحاول الخلية الدفع من جلسة Colab أولًا ثم تستخدم `GITHUB_WRITE_TOKEN` تلقائيًا إذا رفضت جلسة shell المصادقة. لا تحفظ القيمة في `remote` أو الملف. إذا فشل الدفع، تعرض الخلية نص Git الآمن وسبب تعذر Secret إن وجد؛ لا تنشئ `release.json` منشورًا ولا تمس فرع `colab-checkpoints` أو وزن الاستئناف. يمكن إعادة تشغيل الخلية نفسها بعد تصحيح صلاحية Secret؛ فهي تستبدل staging المحلي غير المنشور فقط.

تعامل GitHub tokens ككلمات مرور، ويوصي باستخدام fine-grained tokens لتقييد المستودع والصلاحية.[1]

## الإصدار الذي يقرأه الموقع

| الملف | دوره | شرط قبول الموقع |
|---|---|---|
| `artifacts/published/latest.json` | مؤشر الإصدار الأحدث | `release_id` و`release_path` وSHA-256 لملف الإصدار. |
| `<release>/release.json` | تعريف الإصدار وسياقه العلمي | الحالة `published` والنطاق `synthetic-old-permic-character-baseline`. |
| `<release>/metrics.json` | مقاييس `test` الفعلية | SHA-256 يطابق ما أعلنه `release.json`. |
| `<release>/data_contract.json` | بصمات البيانات والخط والفئات | SHA-256 يطابق ما أعلنه `release.json`. |
| `<release>/class_map.json` | تسلسل الفئات والحروف | موجود في الإصدار؛ لا يستخدمه الموقع للاستدلال بعد. |

الموقع يقرأ الإصدارات المقبولة من `colab-results` فقط. فرع `colab-checkpoints` هو للاستئناف ولا يمثل نشر نموذج أو ادعاءً بأن خدمة OCR تعمل.

## حالة واجهة المختبر

تعرض واجهة الموقع metadata متحققًا منه، لكنها لا تقول إن نموذجًا متصلًا بواجهة OCR. لا يُفعّل الاستدلال الفعلي إلا بعد تحميل وزن متوافق مع `class_map.json` في خدمة الموقع، وتوحيد إحداثيات الكشف، واجتياز اختبار تكاملي. حتى ذلك الحين يظل الوصف الصادق: **baseline صناعي، غير مثبت على المخطوطات التاريخية**.
