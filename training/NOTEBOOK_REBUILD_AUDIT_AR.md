# تدقيق إعادة بناء دفتر Colab الموحد

## الغاية

يعيد هذا التدقيق بناء دفتر `old_permic_synthetic_generation.ipynb` بوصفه **مصدر الحقيقة التنفيذي الوحيد** لمسار Colab: استنساخ الكود، التوليد الصناعي الحرفي، التحقق، التدريب، التقييم، حفظ الاستئناف، ونشر نتائج مصرح بها فقط. لا يسجل أي وزن أو مقياس أو ادعاء OCR قبل أن ينتجه التنفيذ فعلًا.

## ما احتُفظ به من دفتر التدريب السابق

| المكوّن | وضعه في النسخة الجديدة | سبب الاحتفاظ أو التغيير |
|---|---|---|
| فحص CUDA الإلزامي | يُحتفظ به ويأتي قبل التدريب | يمنع تشغيل تجربة كبيرة على CPU دون قصد. |
| تثبيت الاعتمادات في بيئة نظيفة | يُعاد بناؤه لخلايا Colab صريحة | يجعل النسخة قابلة للتشغيل من مشروع مستنسخ حديثًا. |
| التحقق من `class_map.json` ووسوم YOLO | يُحتفظ به ويوسع إلى تقرير موثق | ترتيب الفئات والوسوم عقد لا يجوز تغييره عند الاستئناف. |
| معاينة الصناديق | يُحتفظ بها مع اختيار عينة محددة البذرة | الفحص البصري سابق للتدريب وليس نتيجة شكلية. |
| حفظ `last.pt` ذريًا إلى Drive | يُحتفظ به كطبقة الاستئناف الأساسية | Google Drive هو وجهة الحفظ السريع أثناء التدريب، لا GitHub. |
| الاستئناف المتحقق من بصمة خريطة الفئات | يُحتفظ به ويضاف إليه بصمة البيانات والمولد | يمنع استئناف وزن على فئات أو بيانات غير مطابقة. |
| تقييم `test` وتصدير ONNX | يُحتفظ به ويضاف تقرير مقاييس قابل للنشر | لا يُعرض وزن في الموقع قبل قياس مستقل وتطابق العقود. |
| واجهة Gradio التجريبية | تُحوّل إلى خطوة اختيارية لاحقة | التطبيق هو واجهة العرض الدائمة؛ الواجهة المؤقتة ليست مسار نشر. |

## ما كان ناقصًا في الدفتر الموحد الحالي

الدفتر الحالي يستدعي المولد الحقيقي ويحافظ على المراحل S0 وS0-d1 وS1 وS2، لكنه يفترض وجود المشروع والخط محليًا، ولا يهيئ Colab من مستودع خاص، ولا يكتب عقدًا موحدًا لنتيجة التدريب، ولا يحتفظ بالـ checkpoints خارج جلسة Colab، ولا ينشر نتائج التدريب المصادق عليها إلى GitHub. كما أن التدريب الحالي لا يميز بين **حفظ الاستئناف المتكرر** و**نشر إصدار مكتمل**.

## عقد الأصول المقترح

> لا تُرفع حزمة الصور الصناعية كاملة إلى GitHub. ينسخ Colab المشروع ثم يولد البيانات محليًا؛ وتبقى البيانات الضخمة في Drive عند الحاجة إلى الاستئناف. لا ينشر إلى GitHub إلا وصف الإصدار، القياسات، خريطة الفئات المطابقة، صور معاينة منتقاة، والوزن أو التصدير المقبول ضمن حد التخزين المتفق عليه.

| الأصل | الوجهة الأساسية | متى يكتب | شرط القبول |
|---|---|---|---|
| `last.pt` و`results.csv` وبيان الاستئناف | Google Drive | بعد حفظ نموذج أثناء التدريب | تطابق SHA-256 لخريطة الفئات وبصمة dataset. |
| الحزمة الصناعية | مساحة Colab ثم Drive اختياريًا | بعد اجتياز المدقق | manifest و`assets.jsonl` ووسوم صحيحة؛ لا ترفع إلى GitHub. |
| `metrics.json` و`release.json` | GitHub | بعد تقييم test فقط | يذكر صراحة أن المصدر صناعي أو حقيقي، ومفتاح إصدار فريد. |
| `class_map.json` و`data_contract.json` | GitHub | مع الإصدار | بصمات تطابق ما استُخدم في التدريب. |
| `best.pt` و`best.onnx` | Drive أولًا؛ GitHub فقط إذا اجتاز حد الحجم والسياسة | بعد قبول التقييم | لا يوصف بأنه وزن مخطوطات حقيقية ما لم تكن بيانات الاختبار كذلك. |
| معاينات PNG ومخططات التقييم | GitHub أو تخزين الموقع | بعد التقييم | مرتبطة بـ `release.json` وبصمات SHA-256. |

## المزامنة بين GitHub والموقع

اختيار التنفيذ المطلوب هو فحص معرف المشروع كل خمس دقائق للملف الصغير `release.json` عبر واجهة GitHub، ثم تنزيل metadata أو الأصول المدرجة فيه فقط بعد التحقق من البصمة. واجهة GitHub الخاصة بسجل commits تسمح بفحص مستودع خاص عند استخدام token محدود بصلاحية **Contents: read** فقط.[1]

يُحتفَظ بخيار تحديث فوري لاحقًا: يدعم GitHub webhooks لإرسال إشعار إلى خادم خارجي عند وقوع حدث، لكن ذلك يحتاج secret عشوائيًا والتحقق الثابت زمنيًا من ترويسة `X-Hub-Signature-256` قبل معالجة الحمولة.[2] لا تدخل هذه الآلية في النسخة الأولى لأن الطلب الحالي يحدد فحصًا كل خمس دقائق، ويجب أن يكون الفحص Idempotent ولا ينشئ نتيجة جديدة عندما يظل الإصدار نفسه.

## التسلسل التنفيذي الجديد

1. يثبت Colab الحزم ويستنسخ المستودع بعمق محدود، ثم يتحقق من وجود المولد والخط والبصمات.
2. يولد S0 ثم S0-d1 ثم S1 ثم S2، مع مدقق مستقل وقرار قبول صريح لكل مرحلة؛ التدريب baseline يبدأ بـS0 فقط ولا يمزج المراحل تلقائيًا.
3. يحفظ Colab checkpoint إلى Drive بعد كل حفظ نموذج، ويمنع الاستئناف إذا تغيرت بصمة خريطة الفئات أو بيانات التدريب.
4. يقيم `best.pt` على `test` مستقل وينشئ `metrics.json` و`release.json` لا يمكن نشرهما إذا كانت القياسات أو الملفات المطلوبة ناقصة.
5. ينشر المستخدم النتائج المقبولة فقط إلى فرع GitHub مخصص للنتائج أو إلى مسار `artifacts/published/`، من دون تضمين token أو dataset كامل في commit.
6. يتحقق الموقع دوريًا من أحدث `release.json`، ويعرض حالة المصدر والإصدار والوزن والمقاييس كما هي، ولا يعلن تشغيل استدلال فعلي حتى يُحمّل وزن متحقق منه ضمن الخدمة.

## حدود مهنية صريحة

بيانات Unicode الناتجة من خط ليست مخطوطات تاريخية. قد تثبت تجربة baseline سلامة سير البيانات واكتشاف المحارف المرسومة بالخط، لكنها لا تثبت أداء OCR على صفحات برمية أصلية. يبقى اعتماد أي نتيجة على النصوص الأصلية مرهونًا بحزمة صور موسومة ومراجعة بشرية وتقسيم اختبار مستقل.
